# 检索评测语料规格（RecallPort 长期使用模拟）

## 目的
RecallPort 是本地的 AI 长期记忆服务：AI（Claude Code / Codex / ChatGPT 类助手）在日常使用中把值得长期保存的东西 `write` 成一条条"原子记忆"，改口时 `update` 旧记忆，之后用户再问起时 AI 用 `search` 找回来。
我们要做检索优化，需要一份**像真人用一年那样**的记忆库 + 之后会被问到的问题。你要扮演一位具体的用户，生成他的记忆库和问题。

## 你要产出的文件（一个 JSON 文件，路径由任务给出）
```json
{
  "persona": "一句话描述这个用户",
  "today": "2026-11-20",
  "events": [ ... 按时间顺序 ... ],
  "queries": [ ... ]
}
```

### events（目标：200～260 条 write，另含若干 update/summary/delete）
每个事件是下列之一，`key` 在本文件内唯一（如 `m001`），用于被 queries 引用：

- `{"op":"write","key":"m001","title":"","content":"…","tags":["…"],"occurred":"2026-01-14"}`
  - 一条原子记忆。`title` 可为空串，约一半的记忆写 ≤16 字的标题。`tags` 0～3 个，多数 1～2 个或空。
  - `occurred` 为事件发生日期（YYYY-MM-DD），分布在 `today` 之前约 12 个月内，按时间升序排列所有事件。
- `{"op":"update","key":"m001","content":"…","title":"…","occurred":"…"}`
  - 改口/情况变了：AI 用 update 改写旧节点（旧文字自动进入历史）。content 是**改写后的完整新内容**。
- `{"op":"write","key":"m090","supersedes":"m031", ...}`
  - **AI 没发现旧记忆，只是追加了一条新的**：旧节点 m031 仍然留在库里（这是现实中很常见的情况）。`supersedes` 只是给评测用的标注，不进库。
- `{"op":"summary","key":"s01","title":"≤16字名称","content":"结论（不是目录）","adopt":["m001","m007",…]}`
  - AI 对一组稳定记忆写的汇总（第 1 层）。整份文件写 10～16 条第 1 层汇总，再写 2～4 条第 2 层汇总（adopt 里放 s 开头的 key）。汇总的 content 要像真 AI 写的：浓缩 + 结论，只转述子节点，**可能含已过期的旧值**（如果它写在改口之前，之后没更新——请故意让 2～3 条汇总是这样的）。
- `{"op":"delete","key":"m055"}`：用户要求忘掉（隐私、写错了），3～5 条。

### 记忆内容要求（这是质量的关键）
- 像真实 AI 写的：1～3 句完整的话，说清「谁/什么/为什么/结果」，用用户的语言。**中文用户主要写中文，夹杂英文专有名词、代码、报错原文**；英文用户写英文。允许少量跨语言。
- 内容覆盖真实生活的**长尾**，不要全是同一类：工作/项目决策、配置与环境、Bug 根因与修复、偏好与约束、人物（同事/家人/朋友的信息、别人的偏好——这些是"别人的"，不是用户本人）、日程与预订、金额与账号、健康、购物、学习、旅行、爱好、计划与目标……按你这个用户的人设分配。
- **含数字/名称/型号/日期/地点/金额的具体事实占一半以上**（因为之后会被问到）。
- 约 10% 是"低价值噪声"：一次性的杂事、天气、情绪、寒暄式总结（真实用户库里确实有）。
- **近似干扰**（重要）：至少 12 组，同一类事物有多个相似实例（如两辆车、两个客户、两个项目都用了 Redis、同事 A 和同事 B 的口味、去年和今年的同类开销），措辞相近但事实不同。
- **改口**：约 15% 的事实随时间变化。其中约 2/3 用 `update`，约 1/3 是 AI 没发现而追加（`supersedes`）。改口后的新值必须和旧值明显不同（数字/地点/人/决定变了），最好有些旧新记忆措辞很接近。
- 约 6 条记忆非常长（200～400 字，如一次调试复盘、一份计划），其余多数 30～120 字。

### queries（目标：70～90 条）
问题是**用户过一段时间后再问起时，AI 会发出的 search 查询**。**不要对着记忆原文抄词**：想象你不记得原文怎么写的，只记得大意。每条：
```json
{"id":"q001","qs":["主查询","可选的第二种说法","可选的第三种说法"],"type":"…","gold":["m012"],"stale":[],"note":"为什么这样问/期望什么"}
```
- `qs`：1 条是 AI 的第一次查询；**同时再给 1～2 条同义改写放在同一个数组里**（`qs[0]` 是首次查询，其余是 AI 觉得没找到时的换说法）。查询可以是完整问句，也可以是 AI 常用的关键词式（"Hetzner 月费"、"redis 超时 根因"）。
- `type` 取值及大致数量（每类都要有）：
  - `direct`（≈10）问法和记忆接近，基础事实。
  - `paraphrase`（≈14）同义/换词，**首次查询与目标记忆几乎不共享实词**（如记忆写"年薪 38 万"，问"收入多少"）。
  - `vague`（≈8）只记得大意或上下文："上次修那个连不上的问题是怎么回事"。
  - `keyword`（≈8）纯关键词/型号/报错/人名。
  - `crosslang`（≈6）问题与记忆语言不同（中问英、英问中）。
  - `temporal`（≈6）带时间限定："三月份那次…"、"去年冬天…"；gold 必须是该时间段的那条。
  - `latest`（≈10）问"现在/目前/最新"的值。gold = 改口后的新值节点（update 过的 key，或 supersedes 里的新 key），`stale` = 追加式改口里的旧节点 key（update 式的没有 stale）。
  - `history`（≈4）问"以前/最初/之前是什么"：gold = 被 update 的 key（旧值在它的历史里），`note` 里写明旧值是什么。
  - `overview`（≈6）概览/多点答案："我在 X 上做过哪些决定"，gold 有 2～5 个 key（尽量覆盖一个汇总的 adopt 子节点）。
  - `multihop`（≈4）要组合两条记忆才能答，gold 两个 key。
  - `neardup`（≈8）问近似干扰组里的某一个实例（"小王爱吃什么" vs "小李爱吃什么"，"A 客户的报价"）；gold 是正确的那个，`stale` 里放**最容易混淆的另一个实例**的 key。
  - `absent`（≈10）**库里没有答案**的问题：一半是完全无关的话题，一半是**话题在库里但具体事实没存过**（如库里有他的猫，但没存猫的体重）。`gold` 为 `[]`。注意：要确保真的没存过，且被 delete 的内容也属于 absent。
- gold 必须指向**存在于库里（没被 delete）的 key**，且确实包含答案；被 delete 的内容相关问题归 absent。
- 不要写 gold 为空却其实库里有答案的问题。

## 最后自检（务必做）
用 python 校验：JSON 合法；key 唯一；update/delete/adopt/supersedes/gold/stale 引用的 key 都已在之前出现；events 按 occurred 升序（update 的 occurred 不早于原节点）；每个 query 的 qs 非空；统计各 type 数量。有问题就改。最后只回复：文件路径、write 条数、update/supersede/summary/delete 数、query 总数及各类型数，以及你认为数据里最难的 3 个问题。
